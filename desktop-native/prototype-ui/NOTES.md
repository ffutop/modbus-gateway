## 第一轮（2026-10-04）

**问题**：作为"完整管理控制台"，主界面应该以什么为主线组织？

比较了 A 报文优先（顶部标签 + 三栏抓包）、B 设备工作台（对象树 + 寄存器网格）、C 双联视图（报文 ⇄ 寄存器联动）。

**结论**：选 C 的联动。补充要求：

1. 网关是代理，一次请求包含上游（主站 ↔ 网关）和下游（网关 ↔ 设备）两段 Modbus 报文，两段都要能看到。
2. 先选链路，再看具体请求。
3. 以模拟模型为后端的下游比较特殊（进程内、没有线路帧），需要有专属的视觉表达。
4. 配置要可视化编辑，并能保存、应用和重启。

A、B 已删除。

## 第二轮（2026-10-04）

**问题**：链路怎么选？两段报文怎么呈现？模型怎么区分？配置编辑长什么样？

| 方案 | 选链路 | 两段报文 | 模型的表达 |
|---|---|---|---|
| C1 | 左侧链路列表（网关 → 下游；模型单独汇总），主站用标签筛选 | 时序图：主站 / 网关 / 设备三条泳道，四个箭头带帧字节与耗时 | 第三条泳道是虚线的"模型（进程内）"，箭头上写操作而不是字节 |
| C2 | 顶部拓扑图（主站 → 网关 → 下游 → 模型），点节点组合筛选 | 上下游帧左右对照，标出网关改写的字段（帧格式、事务号、CRC） | 拓扑中多个下游连到同一个模型节点；下游段写明"进程内调用" |

两个方案共用：寄存器区区分"模型 · 权威数据 · 可写"和"真实设备 · 观测值（来自读响应）"；配置模块包含对象树、表单、即时校验、变更列表、保存、保存并重启网关（进程内重启，有确认框）。

**结论**：选 C1（链路列表 + 时序图）；选中链路后，在右侧（请求和寄存器两栏）的顶部放 C2 风格的拓扑图，只画当前网关，并可以点击节点进一步筛选。配置在可视化之外，还要提供直接编辑原始 config.yaml 的方式。C2 已删除。

## 第三轮（2026-10-04）

**问题**：组合后的布局是否顺手？两种配置编辑方式如何共存？

- 联动：左侧链路列表 → 右侧顶部是单网关拓扑（点击主站、下游或模型节点筛选，再点一次取消；连线的速率和颜色随另一侧的选择变化）→ 下方是请求时序图与寄存器。
- 配置：同一份草稿，有"可视化 / config.yaml"两种模式。草稿是真实的 `config.Config`，校验使用真实的 `ParseDraft` 和 `Problems`。
  - 可视化编辑后，进入原始模式时按规范格式重新生成 YAML，注释不会保留。
  - 原始模式下的修改能解析时，实时同步到表单；不能解析时，既不能保存，也不能切回可视化，但可以"放弃文本修改"。
  - 在原始模式下保存，会原样写入文件，保留注释和格式。

**状态**：第三轮原型已完成，等待维护者审查（2026-10-04）。以下是本轮实现的设计，审查通过前不算最终结论。

## 第四轮：P0 / P1 调整（2026-10-04）

沿用已选定的链路列表、顶部拓扑和双联视图；以请求经过的路径、地址和数据来源为诊断主线。本轮只修改原型，没有修改真实网关或根目录配置。

- **Slave ID**：称重仪下游路由 `9,10`，按 ID 选择请求与寄存器；同一下游不同 ID 的值不混合。左树与拓扑显示路由表达式，时序图显示实际请求 ID。
- **Injector**：模拟写入只修改映射目标；显示“保持寄存器 @16 → 输入寄存器 @76 ×2”，自动切换目标表并滚动到关联范围。配置可编辑源表、源地址、数量、目标表、目标地址，支持添加与删除；源表切换自动选择对应目标表，校验仍由真实 `Problems` 执行，包括跨入口目标冲突。
- **数据时间语义**：模型显示当前值；真实设备显示所有主站最近一次成功读取的值。主站筛选不改变读值，写入回显不当作读取确认。独立的“本请求”列保留选中请求的历史读值或写值。
- **报文**：时序图保留方向与时间，完整四段 ADU 在展开区显示，按 8 字节分行并提供字段解码及复制。缺失帧区分无路由、进程内调用、无响应和未采集。
- **列表**：增加表头，寄存器对象、来源、Slave ID 与四张表分行布局；新增暂停跟随、恢复实时、仅异常与清除筛选。窄窗口的配置选项折行，映射表改为纵向字段，不靠缩小字号容纳。
- **配置生命周期**：未保存 → 已保存待应用 → 应用中 → 已生效；失败保留旧运行基线与待应用变更，持续显示失败网关、启动原因和定位入口，允许重试。保存不会清除待应用差异；共享模型变更按引用关系列出受影响网关。
- **错误定位**：可视化问题位于顶部可滚动问题区，可点击定位对象和字段；原始模式显示对象、字段、非法值和行号，可跳到 YAML 出错位置。
- **YAML**：原始保存保留文本；可视化修改通过 YAML 节点更新，保留注释及未进入表单的高级字段，但缩进格式可能重排。v0 保持原文编辑，不隐式升级到 v1。

删去重复“进程内”文字和原始编辑区冗余说明；弱化每行重复的“正常”。图中的数据、保存与重启仍是模拟行为：没有实际写入 config.yaml、重建网关或连接真实设备，模拟重启仍暂停共同的流量发生器。复制按钮接 Gio 剪贴板，系统剪贴板与键盘走查未完成。动效没有验收。

离屏状态包含设备 ID 9/10、模型、injector、超时、配置错误、映射冲突及修复、保存待应用、确认、失败、重试、应用中和生效。截图生成过程还通过按钮事件及断言核对映射增删和配置状态转换。

证据目录：`/private/tmp/modmux-ui-adjusted/`（1440×900）和 `/private/tmp/modmux-ui-adjusted-narrow/`（1100×680），均按 2 倍像素渲染。完成一轮独立视觉评审，不打分；采纳失败原因与定位入口的反馈。常用标签与按钮在两种尺寸下没有明显截断或重叠。完整原生交互与真实后端应用能力仍需后续验证。P2 的大规模拓扑、多个上游入口与状态体系扩展未纳入本轮。

## 第八轮：统一文字度量与基线

复现信号：同为 13sp 的菜单文字在 2 倍渲染下，居中后基线为文件 31px、编辑 38px、查看 33px、网关 31px；回归测试修复前在 1 / 1.5 / 2 倍缩放均失败。

修复：
- 普通 UI 明确平台中文字体优先顺序：macOS PingFang SC，Windows Microsoft YaHei UI / Segoe UI，其他平台 Noto Sans CJK SC / Noto Sans；缺失时仍保留 Go 与系统回退。没有下载或绑定字体文件，跨操作系统外观不保证完全一致。
